# M1：多设备绑定记录（2026-10-25）

本记录描述启动语音实验前的状态。后续所有者已确认音箱实际播报与终端 Agent 回复一致，更新见[首次语音记录](2026-10-25-m1-voice.md)。

## 所有者实测与剩余边界

所有者在可选入口中完成短信验证，设备列表返回两台 L05C；通过改变当前音箱的名称，确认对应的云端设备条目。两个条目的 `model` 和 `online` 均为空；不能据此判断离线。账号、设备标识、实际设备名及原始输出仅保留本地。

这确认了账号设备查询与人工目标识别；尚未确认 MIOT 标识对应、云端对话轮询、Agent 回复及亲耳听到 TTS。固件继续使用已记录的 1.62.28。

## 源码问题与最小修复

固定 [XiaoAiAgent c856d2a 的 speaker.py](https://github.com/Nex-Z/XiaoAiAgent/blob/c856d2a39d156299d0b7e50a84e6421834a64004/src/xiaomi/speaker.py) 在设备没有直接 MIOT 标识时，按型号或名称取第一个 MiIO 设备。显式指定小爱云端 `deviceID` 并不能消除这一阶段的歧义。

本次新增 `device_binding.py`，通过可选入口安装一个窄范围运行时子类，只更改数字 MIOT DID 的解析。优先使用选中设备直接返回的一致数字标识；否则名称必须在两个列表中唯一对应，已提供的型号不得冲突。重复、缺失、冲突或查询失败均停止绑定，错误不带设备标识或原始响应。原生协议和 TTS 发送仍由独立上游提供，其跟踪源码没有修改。

## 实际软件验证

- 原上游的离线复现：使用两台同型号、不同名称的模拟设备，预期数字目标为 `202`，原代码返回 `101`，断言失败。没有请求账号或设备。
- 修复后的实际上游子类使用同一组模拟数据，返回 `202`；确认 FastAPI lifespan 也引用替换后的类，仅导入代码，无服务启动。
- Windows 原 M0 环境：60 项测试中 56 项通过、4 项可选依赖测试跳过。独立 Python 3.12.15 + 固定 MiService 环境：60 项全部通过。
- 新增回归覆盖：相同型号的另一台设备排在前面、直接标识、同名歧义、型号冲突、标识冲突、缺失字段及查询异常脱敏。监听入口的原有测试同时验证子类已安装。

这些离线结果不代表真实 MIOT 对应或 TTS 已通过。下一步由所有者在保留凭据的终端设置已确认的 `MI_DID`，按[实验 003](../003-bridge.md)启动一次语音实验；改名尚未同步时先完成核对。
