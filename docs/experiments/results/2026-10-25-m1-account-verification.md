# M1：账号验证兼容性记录（2026-10-25）

## 已观察的问题与证据边界

设备所有者在独立 XiaoAiAgent 环境执行 `main.py --list-devices`，内嵌 `MiAccount.login` 读取 `resp['userId']` 时抛出 `KeyError`。此证据只说明响应缺少预期字段，没有记录或公开原始响应，不能断言本次密码错误、二次验证或具体风控原因。

固定的 [XiaoAiAgent c856d2a](https://github.com/Nex-Z/XiaoAiAgent/tree/c856d2a39d156299d0b7e50a84e6421834a64004) 假定登录成功响应含 `userId`。社区 [xiaogpt issue #469](https://github.com/yihong0618/xiaogpt/issues/469) 展示过 `code=0` 同时包含 `notificationUrl`、没有最终用户凭证的验证响应；这是可能原因的来源，不是本账号的响应。

## 本次修改

- 新增可选启动脚本，运行时替换独立上游导出的账号类；上游跟踪源码保持原样，不复制其实现。
- 使用 MIT 的 [Yonsm/MiService a1727f7](https://github.com/Yonsm/MiService/tree/a1727f7817819cae89f20ea197c030aaa199b96d)。已核对该提交的 `miaccount.py`、依赖和 LICENSE，源码版本 3.0.2；当时 PyPI 为 3.0.1，因此使用固定提交源码压缩包及 SHA-256，而不是浮动版本。
- 短信／邮箱验证由该库完成，隐藏输入回调只在所有者的终端读取验证码；不关闭账号安全验证。适配器验证初始验证地址属于官方 HTTPS 主机，并将失败归为有限原因和数值代码，不输出响应、链接或原始异常。
- 入口在导入上游前检查凭据，监听还必须显式指定设备并与实际配置一致；账号错误即使被上游捕获，入口也返回失败码。设备查询直接调用现有 `MiNAService`，避免上游错误处理建议关闭二次验证。M0 仍无第三方运行依赖。

## 软件验证

Windows 上分别在原 M0 环境和独立 Python 3.12.15 环境执行完整 `unittest` 套件：M0 运行 53 项，其中 49 项通过、4 项可选契约测试跳过；M1 使用真实固定库，53 项全部通过。覆盖模拟额外验证、OTP 回调、原生请求契约、凭据／验证码／限流响应分类、异常内容脱敏、不可信验证地址、设备配置一致性、查询输出、预检与退出码。初始未登录响应的 `70016` 不直接当作密码错误，只对提交凭据后的响应作该分类。

另外导入真实固定 XiaoAiAgent，确认设备查询和监听模块使用替换后的账号类；只导入模块，不执行登录、启动 HTTP 服务或访问设备。可选依赖 `pip check` 通过。CI 增加独立的 Python 3.12 可选依赖测试任务，普通跨平台任务保持不安装该依赖。

这些结果不证明真实验证码发送、账号登录、设备列表、固件 TTS 或实际播报成功。库的官方验证流程可能随服务端变化，需要所有者按[操作命令](../003-bridge.md#可选短信邮箱验证入口)重试。所有凭据、验证码、设备列表和 `.mi.token` 保留本地。
